# ui-reskin-collab

設計師在**別人擁有程式邏輯**的既有專案上做 UI 換皮 / 改視覺(配色、字體、排版、主題)時的協作流程 skill。
核心:**只動視覺層,不踩工程師的邏輯**(資料 / API / 型別 / 狀態 / business logic),而且讓對方好 review、信任你的改動。

## 核心心智模型

> **視覺層是你的,邏輯層是工程師的。** 但這條線每個 codebase 畫的位置不同 —— 先找出「這個專案」的線,再開工。

| 你能動的「視覺層」 | 工程師的「邏輯層」(別碰) |
|---|---|
| 樣式 / template / CSS / class | 資料抓取(fetch / API client) |
| design token / 主題變數 / 配色 | adapter / mapper(資料轉換) |
| 共用視覺元件、圖檔、字體 | 型別 / schema / 資料模型 |
| 排版 / RWD / 間距 / 動效 | 狀態 store、business logic、即時資料 |

**鐵則:改 token 不改 class(改中央樣式源,不散改);改視覺不改 logic。**

## 怎麼用

接手既有專案改 UI、跟工程師 / RD 合作改前端、「我只想改 UI 不要動到後端」時觸發。

六個步驟:

0. **進場先探勘邊界**(最重要)— 找出這專案哪裡是視覺、哪裡是邏輯、token 在哪,寫成「邊界地圖」。沒文件就**推斷 + 拿去跟工程師確認**,別憑上個專案的假設動手。
1. **改 UI 鐵律** — 改中央樣式源、對齊設計來源、重用既有元件、不硬寫值。(專案沒 token 架構時,先反建 token 層,且第一輪「視覺零變化」只換寫法。)
2. **隔離分支 + 變更 log** — 不直接改 main,維護給工程師 review 的變更 log。
3. **每天 pull 主線** — 讓衝突小而可控;視覺衝突以你為主,邏輯衝突保留工程師的。
4. **被邏輯卡住開「請求單」** — 不自己改後端,寫結構化需求交接。
5. **驗證再交付** — typecheck / build / lint + 瀏覽器實際操作,不主動 deploy。

## 為什麼有價值

最大價值是**邊界透明 + 交接清楚** → 工程師信任建立,後面 80% 衝突與來回都不會發生。
最大風險是**憑上一個專案的假設動手**。
